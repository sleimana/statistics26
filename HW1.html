6 · Discussion: one-way function vs. hash function

  

  
What the toy shows. Scalar multiplication is deterministic and easy in the forward direction: double-and-add needs about log₂k doublings and additions. On the toy curve the inverse problem (recover k from Q) is trivial, because the group has only a handful of elements and a table of all multiples (Section 4) inverts it. On secp256k1 the group has n ≈ 2²⁵⁶ elements, and the best known general algorithms (Pollard's rho, baby-step giant-step) need about √n ≈ 2¹²⁸ group operations. That is the Elliptic Curve Discrete Logarithm Problem (ECDLP).

  
Properties that matter for a one-way function: determinism, efficient evaluation, and hardness of inversion. A further requirement is that the outputs carry no usable information about k, and "looking random" is not enough for that. That is why the frequency, bit-balance and correlation tables are only weak heuristics. They can reveal a broken design (strong bias, visible correlation), but passing them never proves one-wayness.

  
Properties specific to hash functions: arbitrary-length input with a fixed-length digest, collision resistance, second-preimage resistance and the avalanche effect (one input bit flips about 50% of the output bits). Scalar multiplication is a bijection from {1,…,n−1} onto the non-zero points of the subgroup, so it has no collisions inside that range, but k and k+n always collide, by design. It is also homomorphic: (a+b)G = aG + bG. A hash must never have such algebraic structure, while signatures and key agreement (ECDSA, ECDH) depend on exactly this structure. The avalanche measurement in Section 4 shows "chaotic" bit changes, but they come from modular reduction, not from a designed diffusion layer. Together with the homomorphism, this means ECC outputs should not be used as hash outputs, and hash outputs cannot replace public keys.

5 · Roles of the standards and primitives

  

    
ComponentCategoryWhat it does in the wallet

    
BIP-39encoding + key stretchingEncodes 128–256 bits of entropy (plus a SHA-256 checksum of ENT/32 bits) as 12–24 words from a 2048-word list. The words are then stretched with PBKDF2-HMAC-SHA512 (2048 iterations, salt "mnemonic"+passphrase) into a 512-bit seed. The words are a human backup format, not the key itself.

    
BIP-32key derivationHMAC-SHA512("Bitcoin seed", seed) gives the master private key and chain code. CKD functions derive a tree of child keys. Hardened children (index ≥ 2³¹) use the parent private key, so a leaked child key plus the extended public key cannot climb the tree.

    
BIP-44conventionFixes the meaning of tree levels: m / purpose' / coin_type' / account' / change / index. For Ethereum this is m/44'/60'/0'/0/i, which lets different wallets find the same accounts.

    
secp256k1public-key cryptographyQ = kG maps the 256-bit private scalar to a public point (Exercise 1, on a real curve). It also provides ECDSA signatures, which prove ownership without revealing k.

    
Keccak-256hashingHashes the 64-byte uncompressed public key. The last 20 bytes are the address. This shortens the identifier, and because only a hash is published until the first transaction, it hides the public key behind a one-way function.

    
EIP-55checksum (in the encoding)Uses upper/lower case of the hex letters to carry bits of Keccak-256(lowercase address). Backward compatible (case-insensitive parsers still work) and detects almost all typos.

  

  
Five notions that must not be confused

  
    
    
  • Key generation creates fresh secret randomness: the entropy behind the mnemonic. It is the only step that needs a good random source.
    • 
    
  • Key derivation deterministically turns one secret into others (PBKDF2, BIP-32 CKD). There is no new randomness, and the same input always gives the same keys. That is why a single backup restores every account.
    • 
    
  • Public-key cryptography is an asymmetric relation (k secret, Q = kG public) with a trapdoor-free hard inverse. It enables signatures.
    • 
    
  • Hashing is a keyless, fixed-length, one-way, collision-resistant compression (Keccak-256, SHA-256, SHA-512 inside HMAC/PBKDF2).
    • 
    
  • Checksums detect accidental errors and are not security (the BIP-39 checksum bits, EIP-55 capitalisation). Encoding is a reversible change of representation with no secrecy (words ↔ bits, hex, mixed case).
    • 
  

  
How they fit together

  
Each step solves a different problem. Usability: words humans can write down. Brute-force cost and passphrase support: PBKDF2. Many accounts from one backup: BIP-32/44. Ownership proofs: secp256k1/ECDSA. Short, uniform identifiers: Keccak. Typo safety: EIP-55. No single primitive provides all of these, and reusing one primitive for several jobs (for example a hash as a signature) would break the security arguments of each.

  
Statistical properties

  
Section 2 measures what the security model predicts. Seed bits, private keys and address nibbles are indistinguishable from uniform (χ² tests do not reject uniformity, about 50% ones per bit position). A one-character change in the passphrase flips about half of the seed and address bits (avalanche, inherited from HMAC-SHA512 and Keccak). EIP-55 capitalises each hex letter with probability ½, because the capitalisation is a hash bit. The mnemonic words themselves are not uniform text: they are a fixed dictionary, and the last word carries checksum bits.

  
Temporal and historical context

  

    
1977 — RSA: the first practical public-key system, based on integer factorisation. ECC (Koblitz, Miller, 1985) later gave the same security with far shorter keys.

    
2001 — SHA-2 (SHA-256/SHA-512): NIST's Merkle–Damgård hash family, used here inside HMAC-SHA512 and PBKDF2 (BIP-39/32) and for the BIP-39 checksum.

    
2008–2012 — Keccak wins the SHA-3 competition (announced Oct 2012). 2012 — BIP-32 HD wallets.

    
2013 — BIP-39 mnemonics. 2014 — BIP-44 multi-account paths. Ethereum's design (2014) adopted Keccak-256 before the SHA-3 standard was final.

    
2015 — FIPS 202 (SHA-3) standardises Keccak with a different domain-separation padding (0x06 instead of 0x01), so SHA3-256 ≠ Keccak-256 (Section 4). 2016 — EIP-55 checksummed addresses.

  

  
SHA-2 vs Keccak / SHA-3

  
SHA-2 is a Merkle–Damgård construction over a Davies–Meyer compression function. It is vulnerable to length extension, which is why HMAC is used for keyed hashing. Keccak is a sponge over the 1600-bit permutation Keccak-f, with rate 1088 / capacity 512 for the 256-bit variant. It resists length extension and gives SHA-3 a design independent of SHA-2. Ethereum's "SHA3" opcode is in fact Keccak-256 with the original padding.
